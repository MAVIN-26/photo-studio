# REST API LumenBook

Базовый путь — `/api/v1`. Формат запросов и ответов — JSON, кроме ответов без тела. Модель данных и бизнес-правила описаны в [архитектуре](ARCHITECTURE.md).

## Общие соглашения

- Идентификаторы — UUID. Даты — `YYYY-MM-DD`, время — ISO 8601 с явным смещением, например `2026-11-20T12:00:00+03:00`.
- Денежные суммы — целые копейки, валюта — `RUB`. Поля оканчиваются на `_minor`; `200000` означает 2000 ₽.
- Неизвестные поля запросов отклоняются. `role`, `user_id`, `status`, цена и итоговая сумма клиентом не назначаются.
- Сессия передаётся cookie. Все POST и PATCH требуют `X-CSRF-Token`, включая вход и регистрацию. Токен выдаётся через `/auth/csrf`.
- Операции существующих броней и блокировок требуют поле `version`. Изменение зала также требует его версию.
- Версии — положительные целые числа, начинающиеся с 1. Создание брони требует `room_version` для проверки актуальности показанного тарифа.
- Создание ресурса возвращает `201`, его представление и `Location`. Чтение и изменение — `200`. Выход — `204` без тела.
- Для списков броней используются `limit` (по умолчанию 20, от 1 до 100) и `offset` (от 0). Ответ: `items`, `total`, `limit`, `offset`. Порядок стабилен: `starts_at`, затем `id`.
- Каталог четырёх залов возвращается как `items` без пагинации. Расписание ограничено диапазоном до 7 местных календарных дней включительно.
- Ответы с данными пользователя, сессии, доступностью и расписанием имеют `Cache-Control: no-store`.

HTML-страницы: `/`, `/rooms/{id}`, `/login`, `/register`, `/my/bookings`, `/admin`. Документация API: `/docs`, схема OpenAPI: `/openapi.json`.

## Представления ресурсов

### Пользователь

`User`: `id`, `name`, `email` nullable, `phone` nullable, `role`. Хеш пароля и данные серверной сессии никогда не возвращаются.

`Room`: `id`, `name`, `description`, `image_url`, `hourly_price_minor`, `currency`, `opens_at`, `closes_at`, `timezone`, `version`. Часы представлены строками `HH:MM`.

### Бронь

`Booking`: `id`, `room_id`, `user_id` nullable, `starts_at`, `ends_at`, `status`, `source`, `contact_name`, `contact_phone`, `comment`, `hourly_price_minor`, `total_price_minor`, `currency`, `paid_at` nullable, `version`, `created_at`, `updated_at`.

`allowed_actions` содержит доступные пользователю действия: `pay`, `cancel`, `reschedule`, `confirm`. Сервер рассчитывает их по роли, статусу и времени запроса и повторяет проверки при выполнении действия.

Ответы изменяющих операций с бронью содержат `message` — русский текст результата для вывода на экране. При чтении это поле необязательно.

Статусы: `pending_payment` — ожидает оплаты, `paid` — оплата имитирована, `confirmed` — подтверждено администратором, `cancelled` — отменено. Для ручной подтверждённой записи `paid_at` может быть `null`.

### Техническая блокировка

`Block`: `id`, `room_id`, `starts_at`, `ends_at`, `reason` (`cleaning` или `repair`), `status` (`active` или `cancelled`), `version`, `created_at`, `updated_at`.

Для блокировки API отображает внутренний статус `confirmed` как `active`. Техническая блокировка не является клиентской бронью и не появляется в «Моих бронях».

## Аутентификация

| Метод | Путь | Доступ | Запрос | Успех |
| --- | --- | --- | --- | --- |
| GET | `/auth/csrf` | Любой | Без тела | `200`: `csrf_token` |
| POST | `/auth/register` | Гость | `name`, `email` и/или `phone`, `password`, `consent: true` | `201`: `user`, `csrf_token`, `redirect_url`; установлена cookie |
| POST | `/auth/login` | Гость | `identifier`, `password` | `200`: `user`, новый `csrf_token`, `redirect_url`; установлена cookie |
| POST | `/auth/logout` | Любая действующая сессия | Без тела | `204`: сессия и cookie удалены |
| GET | `/auth/me` | Вошедший пользователь | Без тела | `200`: User |

`GET /auth/csrf` создаёт анонимную сессию, если действующей нет, либо возвращает токен текущей. JSON-токен недоступен другому origin. После входа нужно использовать новый CSRF-токен.

Регистрация выполняет автоматический вход: анонимная сессия заменяется авторизованной, CSRF-токен обновляется. Требуется имя 1–100 символов, хотя бы один идентификатор и булево `consent: true`. Время согласия сохраняется в `users.consent_at`. Email нормализуется в нижний регистр, телефон приводится к международному формату с `+` и 8–15 цифрами; пробелы, скобки и дефисы удаляются. Это проверка формата, а не подтверждение владения. Пароль — 8–128 символов. Уникальность идентификаторов обеспечивается БД. При совпадении — `409 IDENTIFIER_ALREADY_EXISTS`.

Форма регистрации содержит одно поле «Телефон или email» и передаёт его как `email` либо `phone`. Повтора пароля нет. `redirect_url` — `/` для клиента и `/admin` для администратора. После регистрации `Location` указывает на `/api/v1/auth/me`. Формы `/login` и `/register` перенаправляют уже вошедшего пользователя по его роли.

Неверный логин или пароль: `401 INVALID_CREDENTIALS`. Вход и регистрация из уже аутентифицированной сессии: `409 ALREADY_AUTHENTICATED`. Отсутствующая или истёкшая сессия для защищённого маршрута: `401 AUTHENTICATION_REQUIRED`.

## Каталог и доступность

| Метод | Путь | Доступ | Результат |
| --- | --- | --- | --- |
| GET | `/rooms` | Любой | `200`: `items` с Room |
| GET | `/rooms/{room_id}` | Любой | `200`: Room |
| GET | `/rooms/{room_id}/availability?date=2026-11-20` | Любой | `200`: доступность часовых слотов |

Каталог возвращает залы в порядке: «Циклорама», «Лофт», «Неон», «Сканди». Дополнительные записи следуют за ними по имени. Цена и часы работы отражают текущие значения БД. Чтение списка и карточки не создаёт сессию. Отсутствующий UUID — `404 ROOM_NOT_FOUND`, некорректный формат UUID — `422 VALIDATION_ERROR`. В HTML-маршруте `/rooms/{room_id}` оба случая отображаются как страница «Зал не найден» с кодом `404`.

Ответ доступности: `room_id`, `date`, `timezone`, `server_now`, `room_version`, `hourly_price_minor`, `currency`, `slots`. Каждый слот содержит только `starts_at`, `ends_at`, `available`. Возвращается сетка часов работы выбранного дня. Уже начавшиеся часы имеют `available: false`; контакты, причины занятости и идентификаторы чужих броней не передаются.

Дата за пределами горизонта: `422 DATE_OUT_OF_RANGE`. Данные доступности — снимок на момент запроса. Даже при `available: true` создание может вернуть `409`, если время успели занять.

## Брони клиента

Доступ — роль `client`. Все запросы ниже ограничены владельцем; `user_id` берётся из сессии. Существующая чужая бронь и несуществующий идентификатор дают одинаковый `404 BOOKING_NOT_FOUND`.

| Метод | Путь | Запрос | Успех |
| --- | --- | --- | --- |
| POST | `/bookings` | CreateBooking | `201`: Booking со статусом `pending_payment` |
| GET | `/bookings?scope=upcoming&limit=20&offset=0` | Необязательные `scope`, `status` | `200`: список Booking |
| GET | `/bookings/{booking_id}` | Без тела | `200`: Booking |
| POST | `/bookings/{booking_id}/pay` | `version` | `200`: Booking со статусом `paid` |
| POST | `/bookings/{booking_id}/cancel` | `version` | `200`: Booking со статусом `cancelled` |
| POST | `/bookings/{booking_id}/reschedule` | `version`, `starts_at`, `ends_at` | `200`: обновлённая Booking |

`CreateBooking`: `room_id`, `room_version`, `starts_at`, `ends_at`, `contact_name`, `contact_phone`, необязательный `comment`. Контактное имя — 1–100 символов, телефон — международный формат, комментарий — до 1000 символов, по умолчанию пустая строка. Пробельное имя недопустимо. Если настройки зала изменились после показа цены, возвращается `409 ROOM_SETTINGS_CHANGED`; бронь не создаётся.

Фильтр `scope`: `all` (по умолчанию), `upcoming` (`starts_at > server_now`) или `past` (`ends_at <= server_now`). Текущая начавшаяся бронь присутствует в `all`. Фильтр `status` принимает один из четырёх статусов и применяется дополнительно.

Пример создания:

```json
{
  "room_id": "8843000a-b862-4619-87bd-2f8ce4ca16f0",
  "room_version": 1,
  "starts_at": "2026-11-20T12:00:00+03:00",
  "ends_at": "2026-11-20T14:00:00+03:00",
  "contact_name": "Демо Клиент",
  "contact_phone": "+79990000001",
  "comment": "Нужен дополнительный источник света"
}
```

Стоимость для зала со ставкой 2000 ₽: `hourly_price_minor = 200000`, `total_price_minor = 400000`, `currency = RUB`.

Правила операций:

- `pay` разрешён только из `pending_payment` и до начала брони. Повторная оплата не создаёт новое событие: возвращается `409 INVALID_BOOKING_STATE` при актуальной версии.
- `cancel` и `reschedule` разрешены из любого неотменённого статуса при остатке **не меньше 24 часов**. При меньшем остатке — `409 CANCELLATION_DEADLINE_PASSED` или `409 RESCHEDULE_DEADLINE_PASSED`.
- При переносе длительность сохраняется, зал не меняется, исходная стоимость сохраняется. Нарушение длительности — `422 DURATION_CHANGE_NOT_ALLOWED`.
- Перенос на занятый интервал даёт `409 SLOT_UNAVAILABLE`, исходная бронь сохраняется.
- Успешный `cancel` освобождает время, но сохраняет запись и `paid_at`. Возврат денег не имитируется.
- Создание не подтверждает бронь автоматически. Кнопка «Оплатить» меняет только состояние оплаты; подтверждение выполняет администратор.

## Операции администратора

Для всех путей `/admin/*` требуется роль `admin`. Клиент получает `403 ADMIN_ACCESS_REQUIRED`.

### Расписание и брони

| Метод | Путь | Запрос | Успех |
| --- | --- | --- | --- |
| GET | `/admin/schedule?date_from=2026-11-20&date_to=2026-11-20` | Обязательные даты, необязательный `room_id` | `200`: расписание |
| GET | `/admin/bookings` | `date_from`, `date_to`, `room_id`, `status`, `limit`, `offset` — необязательные | `200`: список Booking |
| GET | `/admin/bookings/{booking_id}` | Без тела | `200`: Booking |
| POST | `/admin/bookings` | CreateBooking и `source` | `201`: Booking со статусом `confirmed` |
| POST | `/admin/bookings/{booking_id}/confirm` | `version` | `200`: Booking со статусом `confirmed` |
| POST | `/admin/bookings/{booking_id}/cancel` | `version` | `200`: отменённая Booking |
| POST | `/admin/bookings/{booking_id}/reschedule` | `version`, `starts_at`, `ends_at` | `200`: обновлённая Booking |

В ручном создании `source` — `phone`, `telegram` или `vk`; `user_id = null`, `paid_at = null`. Администратор не назначает владельца по телефону. Контакты обязательны, проверка занятости и расчёт стоимости такие же, как для клиента.

`confirm` разрешён только из `paid`. Для ручной брони подтверждение уже выполнено при создании. Администратор отменяет и переносит без ограничения 24 часов; новый интервал проверяется по общим правилам. Перенос сохраняет зал, длительность, цену, статус и `paid_at`.

Ответ расписания: `date_from`, `date_to`, `timezone`, `server_now`, `rooms`, `bookings`, `blocks`. Возвращаются активные записи, пересекающие диапазон местных дат. Свободные часы интерфейс получает из часов работы залов за вычетом занятости и уже начавшихся часов. Списки внутри расписания полные, без пагинации, для выбранного диапазона до 7 дней.

Для списка `/admin/bookings` обе даты передаются вместе либо обе отсутствуют; начальная не позже конечной. Даты фильтруют пересечение интервалов, верхняя граница включительна как календарная дата. Административный просмотр допускает исторические даты и не ограничен горизонтом создания брони.

### Настройки и технические блокировки

| Метод | Путь | Запрос | Успех |
| --- | --- | --- | --- |
| PATCH | `/admin/rooms/{room_id}` | `version` и изменяемые поля RoomSettings | `200`: Room |
| POST | `/admin/blocks` | `room_id`, `starts_at`, `ends_at`, `reason` | `201`: Block |
| GET | `/admin/blocks/{block_id}` | Без тела | `200`: Block |
| POST | `/admin/blocks/{block_id}/cancel` | `version` | `200`: Block со статусом `cancelled` |

`RoomSettings`: `hourly_price_minor`, `opens_at`, `closes_at`. Хотя бы одно изменяемое поле обязательно; пропущенные значения сохраняются, `null` не разрешён. Цена — положительное целое. Часы на целых часах, `09:00 <= opens_at < closes_at <= 23:00`. Настройка не расширяет ограничения режима здания.

Успешная смена цены не меняет старые брони. Конфликт нового расписания с действующими или будущими активными записями — `409 ROOM_SCHEDULE_CONFLICT`. В деталях этой административной ошибки допускаются идентификаторы конфликтующих записей.

Блокировка занимает свободный будущий интервал одного зала на целое число часов в пределах часов работы и горизонта создания. Контактов и цены у неё нет. Пересечение с бронью или другой блокировкой — `409 SLOT_UNAVAILABLE`. Отмена блокировки снимает занятость, запись остаётся в истории. Редактирование интервала блокировки в MVP не предусмотрено.

Повторная отмена уже отменённой блокировки при актуальной версии возвращает `409 INVALID_BLOCK_STATE`.

Физическое удаление броней и блокировок через API отсутствует.

## Ошибки

Общий формат для всех ошибок, включая валидацию FastAPI:

```json
{
  "error": {
    "code": "SLOT_UNAVAILABLE",
    "message": "Выбранное время уже занято. Обновите расписание.",
    "details": []
  }
}
```

`code` — стабильное значение для JavaScript, `message` — русский текст для пользователя, `details` — массив ошибок полей с `field`, `code`, `message`. Ответ не содержит SQL, трассировку, значения паролей и чужие контакты.

| HTTP | Код | Ситуация |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED`, `INVALID_CREDENTIALS` | Нет действующей авторизации или неверный вход |
| 403 | `ADMIN_ACCESS_REQUIRED`, `CLIENT_ACCESS_REQUIRED`, `CSRF_INVALID` | Недостаточная роль или неверный CSRF-токен |
| 404 | `ROOM_NOT_FOUND`, `BOOKING_NOT_FOUND`, `BLOCK_NOT_FOUND` | Ресурс отсутствует либо недоступен текущему владельцу |
| 409 | `IDENTIFIER_ALREADY_EXISTS`, `ALREADY_AUTHENTICATED` | Конфликт учётной записи или сессии |
| 409 | `SLOT_UNAVAILABLE`, `VERSION_CONFLICT` | Занятое время или устаревшая версия |
| 409 | `ROOM_SETTINGS_CHANGED` | Показанная пользователю цена или часы работы устарели |
| 409 | `INVALID_BOOKING_STATE`, `INVALID_BLOCK_STATE` | Действие неприменимо к текущему статусу |
| 409 | `CANCELLATION_DEADLINE_PASSED`, `RESCHEDULE_DEADLINE_PASSED` | До начала менее 24 часов |
| 409 | `ROOM_SCHEDULE_CONFLICT` | Новые часы работы исключают существующие записи |
| 422 | `VALIDATION_ERROR`, `DATE_OUT_OF_RANGE`, `INVALID_TIME_RANGE`, `DURATION_CHANGE_NOT_ALLOWED` | Нарушен формат или правила интервала |
| 503 | `SERVICE_UNAVAILABLE` | БД недоступна либо истёк таймаут блокировки; результат операции нужно проверить чтением |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка; детали остаются в серверном журнале |

При устаревшей версии возвращается `VERSION_CONFLICT` до проверки перехода статуса. Пользователь обновляет данные и заново решает, выполнять ли действие. POST создания брони не следует автоматически повторять после сетевого сбоя: сначала нужно проверить список броней. Ключи идемпотентности не включены в этот контракт MVP.

## Сценарии приёмки контракта

1. Получить CSRF-токен, зарегистрироваться, войти, получить профиль и выйти.
2. Создать бронь и убедиться, что доступность изменилась ещё до оплаты.
3. Отправить два одновременных запроса на один интервал: успешен ровно один, второй получает `409 SLOT_UNAVAILABLE`.
4. Оплатить через заглушку, подтвердить администратором, проверить сохранение `paid_at` и запись события имитации уведомления.
5. Отменить и перенести бронь при остатке ровно 24 часа; при меньшем остатке получить запрет для клиента.
6. Перенести на занятое время и проверить, что старое время осталось за исходной бронью.
7. Создать ручную бронь и блокировку: обе занимают время на клиентской витрине.
8. Сменить цену: стоимость существующей брони не изменилась.
9. Проверить `401`, `403`, `404` для отсутствующей сессии, недостаточной роли и чужой брони.
10. Изменить запись из двух вкладок с одинаковой версией: второе изменение получает `409 VERSION_CONFLICT`.
11. Попытаться закрыть часы работы, в которых есть активная бронь: получить `409 ROOM_SCHEDULE_CONFLICT`.
